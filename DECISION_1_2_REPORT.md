# Decision 1.2: Rate Limiting Strategy for Terraform Provider HTTP Client

## Context

The Devin API v3 may enforce rate limits. The Terraform provider's HTTP client needs a strategy for handling them. We evaluated three options by building PoC implementations and running benchmarks against both a mock rate-limited server and the real Devin API.

## Options Evaluated

| Option | Description | LoC (core) |
|--------|-------------|------------|
| **A — Client-side rate limiter** | `golang.org/x/time/rate` token bucket; pre-limits requests before they hit the API | ~56 |
| **B — React to 429 responses** | No pre-limiting; on 429, reads `Retry-After` header, sleeps, retries with exponential backoff + jitter | ~93 |
| **C — Both** | Client-side limiter as first line of defense + 429 handling as fallback | ~107 |

## Key Findings from Mock Benchmarks

### Option A — Client-Side Rate Limiter
- **Prevents almost all 429s** at the server (only 1–2 edge-case 429s due to timing).
- **Does not retry on 429**, so those edge-case 429s propagate to the caller as failures.
- **Predictable throughput** of ~10 rps matching the configured rate limit.
- **Server load stays constant** at exactly 50 requests regardless of concurrency — no wasted requests.
- **Simplest implementation** at 56 LoC.

### Option B — Retry on 429
- **100% success rate** — every request eventually succeeds via retries.
- **Server load explodes with concurrency**: at concurrency=20, the server sees 122 requests (72 of which are 429s) to complete 50 logical requests — a **2.4x amplification** factor.
- **P99 latency spikes** at high concurrency (up to 4.3s) because many requests must wait through retry backoff.
- Being a "good API citizen" is inversely proportional to concurrency.

### Option C — Combined (Limiter + Retry)
- **100% success rate** (like B) with **minimal server-side impact** (like A).
- Only 3 server-side 429s even at concurrency=20 (vs. 72 for Option B).
- Total server requests stay around 53 (vs. 122 for Option B) — a **6% overhead** vs. **144% overhead**.
- Slightly higher average latency than A due to occasional retry waits, but P99 is much better than B.

## Real Devin API Observations

### Sequential Requests (20 requests, no rate limiting)
- **0/20 requests returned 429** — all succeeded with HTTP 200.
- No `X-RateLimit-Remaining` or `Retry-After` headers observed in responses.
- Average response time: ~60–80ms for the knowledge notes endpoint.
- Some occasional spikes to 1.8s–4.5s (likely cold-start or backend variability).

### Concurrent Burst Tests

| Concurrency | Total | Success | 429s | Other | Duration | RPS |
|-------------|-------|---------|------|-------|----------|-----|
| 5 | 30 | 30 | 0 | 0 | 431ms | 69.6 |
| 10 | 30 | 30 | 0 | 0 | 309ms | 97.2 |
| 20 | 30 | 30 | 0 | 0 | 434ms | 69.1 |
| 50 | 50 | 49 | 0 | 1 (504) | 60.1s | 0.8 |

### Real API Conclusions
1. **The Devin API does not currently return rate limit headers** (`X-RateLimit-Remaining`, `Retry-After`).
2. **No 429s observed** even at 50 concurrent requests — the API has generous rate limits or does not enforce per-key limits at this scale.
3. At very high concurrency (50 simultaneous), one request timed out with a **504 Gateway Timeout**, suggesting the backend can be overwhelmed but responds with 504 rather than 429.
4. Since the API may add stricter rate limits in the future, the provider should be prepared.

## Recommendation: **Option C — Combined**

For a Terraform provider context, **Option C** is the clear winner:

### Why Option C?

1. **Terraform runs batch operations.** `terraform apply` may create/update/delete many resources in parallel (default parallelism=10). Option B alone would cause a **2.4x request amplification** at that concurrency level, hammering the API with unnecessary 429s.

2. **Defense in depth.** The client-side limiter prevents the vast majority of 429s proactively, while the 429 retry logic handles edge cases (race conditions, rate limit changes, burst spikes) gracefully.

3. **API-friendly.** At concurrency=20, Option C generates only 3 extra server requests vs. Option B's 72. This matters for API providers who may tighten rate limits if clients are abusive.

4. **Resilient to configuration drift.** If the API changes its rate limits, the 429 fallback ensures requests still succeed — unlike Option A alone, which would leak 429 errors to Terraform users.

5. **Acceptable complexity.** The 107 LoC implementation is only 14 lines more than Option B and adds significant value. The `golang.org/x/time/rate` dependency is a well-maintained stdlib-adjacent package.

### Recommended Configuration for Production

```go
// Default values for the Terraform provider
const (
    defaultRPS        = 5.0  // Conservative; can be tuned via provider config
    defaultBurst      = 2    // Allow small bursts for Terraform's parallel ops
    defaultMaxRetries = 5    // Sufficient for transient rate limit hits
)
```

### Implementation Notes

- The rate limiter should be **shared across all resources** in a single `terraform apply` run (configured at the provider level, not per-resource).
- Consider making `rps` and `max_retries` configurable via provider schema for users with different API tiers.
- Add logging when 429s are hit so users can tune their configuration.
- The `Retry-After` header should always be respected when present, even if the API doesn't currently send it.
